# 军旗玩法、抽象与接入手册

更新：2026-09-13。总览见 [TECHNICAL_ARCHITECTURE.md](../TECHNICAL_ARCHITECTURE.md)，共享传输端口见 [抽象层使用手册](abstractions.md)。规则基线参考 junqi.app 的双人军旗规则与 Luzhanqi 公开规则说明；棋谱采用中国大学生计算机博弈大赛棋谱标准说明书的 AC2 `INFO[1.0]` 双人军旗格式。

AI 状态：尚未接入可复用引擎，也未定义 `IJunqiAiEngine`。隐藏信息输入必须停留在玩家脱敏视图，不能把权威双方布阵泄露给搜索器；若批准自研，优先验证 ISMCTS/determinization MCTS 基线。评估、资源所有权和建议阶段见 [AI 难度与分析](ai-engines.md)。

## 1. 已实现规则

`JunqiGame` 是独立领域聚合，不继承固定 9×10 象棋棋盘。`JunqiTopology` 以 12×5、A-L/0-4 的 60 个可停点和道路/铁路边表达棋盘；行营与大本营是点属性，山界不是伪造棋位。双方各 25 子，布阵验证军旗位于大本营、地雷位于后两排、炸弹不在第一排，并验证棋种数量、ID 和占位唯一。

已实现普通道路一步、普通棋子铁路直行无阻挡、工兵铁路转弯、行营保护、大本营棋子不可再移动、地雷和军旗不可移动；军衔比较、同级同归于尽、炸弹同归于尽、仅工兵排雷、司令阵亡亮出同方军旗、夺旗胜利、无合法着法判负，以及 `SL=31` 的连续 31 步未交战判负。先手固定为 `JunqiSide.First`。当前没有翻棋变体、四国军棋、裁判第三方、悔棋、和棋、棋钟或手工布阵编辑器；每局由密码学随机数生成一份满足约束的合法私密布阵。

## 2. 分层与抽象

### `JunqiTopology`

- 职责：提供不可变棋位集合、点类型、道路邻接与铁路邻接；非职责：占位、走法、显示坐标和网络编号。
- 输入/输出：输入 `JunqiCell`；越界的 `Kind` 抛出 `ArgumentOutOfRangeException`，邻接查询对未知点返回空集合。拓扑构造后只读，可在任意线程读取，不持有需释放资源。
- 不变量：60 点、每条边双向、无重复边；领域聚合只通过该图判断可达性，UI 绘制和命中使用同一 `JunqiCell`，但不自行推断规则。

### `JunqiGame` 与快照

- 职责：拥有双方私密棋子、轮次、战斗、亮旗、必攻计数与胜负；非职责：玩家鉴权、网络、文件和 Godot 节点。
- 前置条件：标准对局构造器必须收到双方完整合法布阵；`TryMove` 原子验证来源、轮次、占位和路径，非法动作返回带错误文本的失败结果且不修改状态。`Resign` 是领域入口，但当前界面尚未暴露。
- 权限：`JunqiSnapshot` 含双方真实身份，只能留在权威控制器或赛后复盘。直播/UI 必须调用 `ForPlayer(viewer)`；己方、已亮军旗及终局棋子可见，其余身份为 `null`。`ForReplay()` 是明确的全知赛后入口，禁止用于直播。
- 线程与所有权：同步、单线程聚合；每次快照复制集合，不持有外部资源，无需 Dispose。

### `IJunqiMatchController`

- 职责：向 UI 提供玩家视角快照、席位、就绪/连接/提交权限、权威合法落点和 `SubmitMoveAsync` 意图入口；非职责：绘制、文件选择、平台 Lobby 和传输轮询。
- 实现与注入：本地热座使用 `LocalJunqiMatchController`；LAN/Steam 由 `Main` 创建对应 `ITwoPlayerPacketTransport`，再构造 `NetworkJunqiMatchController` 并注入 `JunqiGameScreen`。UI 不得持有 `JunqiGame` 或写快照。
- 事件顺序：合法本地动作先更新权威聚合，再同步触发 `Changed`；客户端动作先发出带期望 Ply 的请求，房主裁决后发送玩家专属状态，客户端验证连续 Ply 后触发 `Changed`。`Message` 只表达连接/拒绝文本，不承载权威状态。
- 权限与错误：`CanSubmitMove` 同时要求已就绪、已连接、未终局且轮到本地席位。畸形、越界、错误角色、重复/跳跃 Ply 或非法布阵被拒绝；业务非法通过 `JunqiSubmitResult` 返回，不用异常表达。取消通过 `CancellationToken` 传播。
- 资源：屏幕拥有控制器；退出树时先解绑事件再 `DisposeAsync`。网络控制器幂等解绑并释放 transport。transport 的 Godot Node 由屏幕挂载以驱动轮询，后台 I/O 不直接操作控件。
- 兼容：军旗线协议使用独立头 `[1, 0x51]` 和有界 JSON；经典 `MatchWireProtocol` 只负责 Lobby 模式协商，不解析军旗状态。协议字段不兼容变更必须提升军旗头版本并同步 fake/ENet/Steam 测试。

房主拥有完整双方布阵并发送不同的玩家视图，客户端终局后才收到双方布局以生成棋谱。这是可信房主模型：认证 transport 能绑定对手，却不能让 P2P 房主对私密布阵“不可见”。若要无信任裁决，应新增中立权威服务，不应把棋规复制到 LAN 与 Steam 适配器。

## 3. UI 与隐私

`JunqiBoardView` 只消费 `JunqiPlayerSnapshot`，道路/铁路绘制与点击命中共享一套投影；旋转只让本地一方位于下方，不改变领域坐标和 AC2 坐标。本地热座在每次换手后覆盖棋盘，当前玩家主动确认后才显示其视图，避免上一方看到下一方身份。网络模式固定显示本地玩家视图。

玩法画廊军旗选项树只有“联机模式（本地联机/局域网联机/Steam 邀请好友）”和“对局记录（最近对局/保存对局）”。联网房间右侧复用共享双人聊天面板，消息固定发送给唯一对手，不显示无意义的接收者选择；聊天帧不进入私密布阵、玩家视图或 AC2 棋谱。军旗目前不启用经典棋钟，所以设置页不显示计时控件。卡片 SVG 是仓库自有的代码原生装饰资源，不编码局面或交互状态。

## 4. AC2 棋谱与文件所有权

`JunqiGameRecord` 保存双方完整初始布阵、主线着法、声明战斗结果、胜者、TL 与 SL。`Replay()` 每次创建新聚合，逐手验证行棋方、路径、战斗、亮旗和胜负；不返回部分可信结果。`JunqiAc2Codec` 写出/读取 `INFO[1.0]`、`AA/AB` 布阵、`MA/MB` 着法、`RA/RB` 战果、`FA/FB` 亮旗和 `EA/EB` 结果，使用 A-L/0-4 坐标及 a-l 棋子代码，文本上限 4 MiB。

`JunqiRecordStore` 是格式与落盘时机所有者，通过共享作用域存储在 `user://games/junqi.standard/records/recent|saved` 以 GB2312（代码页 936）和 `.ac2` 原子写入。recent 最多十局，saved 不自动淘汰；路径加载严格限制在该玩法目录。首次访问只复制并保留旧目录记录。编码失败、磁盘失败只提示/记录，不反向修改胜负。实时双方布阵不得写盘，控制器只在终局且赛后布局齐备时创建记录。

最近记录页允许将已有 recent 追加到 saved；操作前会再次执行 AC2 解码和领域重放，仅在成功后写入新文件及展示 sidecar，原 recent 保留。

## 5. 测试与当前验收状态

运行 `dotnet run --project tests/Xiangqi.Core.Tests/Xiangqi.Core.Tests.csproj`。现有测试覆盖布阵/脱敏、道路与铁路、工兵转弯、行营/大本营、军衔/炸弹/地雷、司令亮旗/夺旗、越界和非法布阵、SL=31、AC2 往返/篡改结果拒绝，以及房主裁决与双方玩家视图。

编译和 fake 联机不等于真实设备验收。仍需在两台设备上验证 LAN、防火墙、Steam 好友邀请与终局布局释放；需人工检查窄屏横向画廊、两种朝向命中、热座遮罩和长棋谱复盘。Android 仅做条件构建时也不能宣称触屏体验已验收。
