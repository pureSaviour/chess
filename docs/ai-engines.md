# AI 难度、分析与后续玩法接入

更新：2026-09-14。本文记录已经落地的经典象棋/五子棋 AI 配置，以及军旗/三国象棋仍处于评估阶段的边界。总览见 [TECHNICAL_ARCHITECTURE.md](../TECHNICAL_ARCHITECTURE.md)，端口契约见 [抽象层使用手册](abstractions.md)。

## 已实现：统一难度与高级搜索

玩家入口使用 `AiDifficultyLevel` 的入门、简单、适中、困难、大师五档，另有自定义档；新安装默认适中。`AiDifficultyProfiles` 是 Application 层的稳定映射，UI 不保存 Pikafish/Rapfi 的内部搜索对象，也不修改权威棋局。

| 档位 | 象棋：时间/深度/候选弱化 | 五子棋：时间/深度/Rapfi strength |
| --- | --- | --- |
| 入门 | 确定性随机合法着，不调用搜索 | 确定性随机合法落点，不调用搜索 |
| 简单 | 0.1 秒 / 1 / 第 8 候选、最多损失 5000 分 | 0.1 秒 / 1 / 1 |
| 适中 | 0.25 秒 / 3 / 第 5 候选、最多损失 1500 分 | 0.25 秒 / 3 / 15 |
| 困难 | 0.8 秒 / 7 / 第 2 候选、最多损失 200 分 | 0.8 秒 / 8 / 60 |
| 大师 | 3 秒 / 不限 / 最佳着 | 3 秒 / 不限 / 100 |

“深度”是搜索层数上限，“时间”是墙钟预算；同时设置时任一限制先到即停止。深度 0 表示不设深度上限，由时间限制迭代加深。固定深度在不同 CPU 上耗时差异很大，因此五档入口不要求玩家理解它，自定义档才直接使用保存的时间与深度。

象棋的 `AiSearchRequest` 输出时间、MultiPV 数和可选深度；`UciProcessAiEngine` 翻译为 `MultiPV` 与 `go movetime ... depth ...`，线程/哈希只由进程适配器消费。入门档直接从权威棋规生成的合法着中稳定选取一个，保证真正适合初学者且不受强引擎静态评估影响；简单到困难可能选用非第一候选，但 `AiGameCoordinator` 会逐个通过权威棋规复验，并限制相对最佳着的分差；没有符合条件的合法候选就回退最佳合法着。

五子棋的 `GomokuAiSearchRequest` 输出时间、最大深度、strength、线程和内存。Rapfi 适配器翻译为对应 `INFO` 参数；Application 只知道有界数值。入门档同样从当前规则逐点复验出的合法落点中稳定选取，不调用 Rapfi；其余档位才使用搜索。引擎坐标仍由 `AiGomokuMatchController.Poll` 在调用线程按当前手数、行棋方、占位、越界和禁手重新执行。进程每次搜索独占，取消/退出杀死进程树，释放幂等。

设置页默认只显示难度及执子、棋钟、棋盘和规则等对局常用项。固定引擎的一键配置、对局时间、复盘每局面时间、深度、线程、内存或哈希放在默认收起的“高级设置”中；不提供路径输入、文件浏览或替代引擎入口。自定义档才直接采用高级区保存的对局时间与深度；复盘时间则独立生效于全部难度，并由象棋和五子棋共用。

兼容策略：旧设置没有 difficulty 键时读取“适中”，原有 think_milliseconds 保留为自定义档数值。新的共享复盘预算使用 `replay_analysis/think_milliseconds`，缺失时默认为 200ms，并限制在 100ms–120s；旧版同名或各引擎私有的 analysis_milliseconds 不迁移，避免恢复过长历史值。旧版保存的 engine_path 仍不读取。运行时只接受安装器管理目录中的 Pikafish 2026-01-02 和 Rapfi 2025-06-15；缺失时引导玩家一键配置。

## 已实现：五子棋复盘胜率图

`IGomokuAiEngine.AnalyzeAsync` 返回黑方胜率、原始估值、深度和当前局面的最佳落点，不返回可写棋局。Rapfi 适配器在同一个短生命周期进程内，以玩家配置的复盘预算、无限深度、单线程和 strength 100 执行正常搜索取得最佳落点，再把进程重置到原局面并用 `YXBOARD + TRACESEARCH` 读取 `Static Eval[Black]` 与 WDL 百分比，避免每个局面重复启动两次进程；它限制行长、有限数值和 0..100% 范围。`GomokuReplayAnalysisCoordinator` 复验最佳落点，串行分析、优先当前选中手、缓存结果、取消旧扫描并抑制陈旧完成，每个未缓存局面后让出 50ms；终局按赢家直接映射 100%/0%/50% 且不标注下一着。它拥有并且只释放引擎一次。

复盘 UI 复用 `ReplayEvaluationGraph`：中线是 50%，上方黑优、下方白优，金色竖线为当前手；棋盘以金色圆环和叉号标注当前局面的最优落点。图表和标记只消费分析结果，不修改 SGF、快照或棋盘。胜率仍是 Rapfi 的静态 NNUE/规则估值，与用于选取最佳落点的完整搜索是两个结果；不同棋盘尺寸和规则的数值不可直接横向比较。

## 尚未实现：军旗 AI

目前未选定可直接嵌入且同时满足本项目双人暗信息规则、许可、Windows/Android、维护和协议要求的成熟引擎。军旗不能把对手真实布阵交给普通完全信息搜索：引擎输入必须是该席位的脱敏视图、公开历史和合法行动集合，输出只是意图，最终仍由权威 `JunqiGame` 裁决。

若自制 C++ 引擎，建议分阶段：先做规则一致性测试与随机合法基线，再做信息集蒙特卡洛树搜索（ISMCTS）或 determinization MCTS；采样必须满足已公开身份、战斗结果、布阵数量和位置约束，使用 UCT/PUCT、启发式 rollout、置换缓存和固定时间预算。训练型方案可再加入自博弈策略/价值网络。难点主要是隐藏信息信念更新、样本偏差和每次模拟的规则吞吐，不是单纯 Alpha-Beta 深度。只有用户批准后才新增独立 `IJunqiAiEngine`。

## 尚未实现：三国象棋 AI

当前未发现可直接支持本项目 135 点三域拓扑、三方轮次、收编/复活、淘汰和既定胜负规则的成熟现成引擎。它不能使用经典 9×10 FEN、红黑 `Opponent()` 或双人零和评分。

若自制 C++ 引擎，建议先实现 Max-N 或 paranoid search 基线，再评估 MCTS。状态键必须包含三方控制权、出生国、存活/淘汰、兵出境状态和当前席位；搜索需要迭代加深、置换表、走法排序、静态评估与时间控制。三人博弈还存在联盟/互害和非零和效用建模，强度调试明显难于经典象棋。只有确认效用定义和性能目标后才设计独立 `IThreeKingdomsAiEngine`，UI 仍只经 `IThreeMatchController.Submit`。

## 测试入口与限制

核心入口是 `dotnet run --project tests/Xiangqi.Core.Tests/Xiangqi.Core.Tests.csproj`，覆盖难度映射、范围错误、搜索参数传递、候选本地复验、五子棋黑方胜率缓存和幂等释放。复盘采用可配置时间预算（默认 200ms）、固定单线程/内存、时间轴防抖、局面间让步、UCI 每帧输出预算及 Rapfi 单进程分析；2026-09-14 的 90 项核心测试、Windows/Android 条件编译和无头 UI smoke 均通过。尚未完成：各档长期棋力标定、图表有窗口视觉和长棋谱帧率验收、Android 原生引擎，以及军旗/三国任何 AI 实现。
